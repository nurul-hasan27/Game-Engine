# engine asset configuration
#
# One asset per line, in the format the parser accepts:
#
#     Texture   <name> <path>
#     Font      <name> <path>
#     Animation <name> <textureName> <frameCount> <speed>
#
# An Animation names a texture rather than a file, so the texture it uses has to
# be declared on an EARLIER line. Declaring it afterwards is a parse error, not
# something resolved later.
#
# frameCount is how many equal columns the texture is cut into, and speed is how
# many game frames pass between animation frames. Both must be positive.
#
# A frame count must divide the texture's width exactly. Frames are one row of
# equal columns, so a width that is not a multiple of the frame count has no
# honest way to be cut, and the loader refuses it rather than rounding. See the
# note on megaman_megaRun below for the case that motivated that rule.
#
# Paths are relative to the directory containing this file, not to the
# process working directory, so this configuration and the library it
# names can be moved together as a unit.
#
# Names are unique across the whole file, not just within a type. A texture
# name and a font name cannot be the same word, because an asset is
# referred to by its name alone.
#
# Names are derived from the path: the containing folder, then the file's
# stem, so mario/ground.png is 'mario_ground'. That keeps them readable
# without consulting the path.
#
# Every file in the committed library is listed, including the three that are
# palette-indexed PNGs (animations_explosion, mario_Flagpole, mario_question).
# They need no special entry: the loader reads them exactly as it reads the
# rest, which is verified by a pixel comparison in the test suite.

# --- animations --------------------------------------------------
#
# Only the three genuinely multi-frame images in the library are declared here.
# Every other image is a single frame, and a one-frame animation is legal but has
# no consumer yet: nothing in the engine has a level file that names animations
# per entity, so declaring thirteen of them would be declaring configuration
# nothing reads.
#
# Each frame count below is the course reference's, and each was checked against
# the committed image before being written down:
#
#   animations_explosion  1152 x 96   1152 / 12 = 96   exact
#   mario_GoombaWalk       100 x 41   100 / 2 = 50    exact
#   mario_GoombaDeath      60 x 26    60 / 2 = 30     exact
#
# megaman_megaRun is deliberately NOT declared, even though the course reference
# declares it as 3 frames. It is 733 pixels wide, and 733 / 3 is 244.33, so the
# frames do not line up. Measured against the actual artwork, its three run
# sprites are 191, 129 and 167 pixels wide, separated by wide transparent
# margins, so a truncating slice would not visibly clip anything - it would place
# each sprite 2 to 6 pixels off the centre it claims, and silently discard the
# final column because 3 x 244 is 732 and not 733. That is a real
# misregistration, so this engine refuses it instead. Re-authoring the strip to a
# width that divides evenly, or adding a frame-offset field to the format, would
# both fix it honestly; rounding the division would not.
Animation animations_explosion_burst   animations_explosion   12  8
Animation mario_GoombaWalk_walk        mario_GoombaWalk      2  8
Animation mario_GoombaDeath_flat       mario_GoombaDeath     2  6

# --- level animations ------------------------------------------------
#
# A level file names an ANIMATION for every tile and every decoration, and names
# one more for the player's bullets. Phase 13 added that format, and until these
# existed a level could not be loaded at all: every record in it would have named
# an animation that was not declared.
#
# All six are single-frame, which is a real thing rather than a placeholder: a
# static tile, a cloud and a bullet are each one picture, and a one-frame
# animation is the honest way to say "this artwork, never advancing". A frame count
# of 1 divides every texture width exactly, so the divisibility rule that made
# megaman_megaRun unloadable is not in tension with any of them.
#
# Each animation's name differs from the texture it uses, because asset names are
# unique across the whole file rather than only within a kind - a texture and an
# animation cannot be the same word, since an asset is referred to by its name
# alone. The `_tile` and `_dec` suffixes are the same convention
# mario_GoombaWalk_walk already established.
#
# Each one has a live consumer: the six lines in levels/level1.txt below that use
# them, and nothing here is declared on the chance that a future level might want
# it. The names are derived from the path, as every other name here is, with the
# frame count appended where a file could plausibly hold more than one strip.
#
#   mario_ground_tile          64 x 64     exactly one grid cell
#   mario_SmallPipe_tile       70 x 70     deliberately NOT a cell, to prove the
#                                            collider and the anchor are both read
#                                            from the animation rather than assumed
#                                            to be 64
#   mario_SmallCloud           70 x 51
#   mario_SmallBush           150 x 68
#   mario_BigBush             186 x 79
#   megaman_megaBuster_shot    32 x 26     the player's bullets
#
# The course's own reference declares a 'Brick' animation, and there is no brick
# artwork anywhere in this library - the reference itself points TexBrick at
# mario/ground.png. So no Brick animation is declared here, and levels/level1.txt
# contains no brick. Inventing one from the ground tile would be a lie about what
# the game contains. See the note on question blocks in LevelLoader.hpp.
Animation mario_ground_tile          mario_ground        1  1
Animation mario_SmallPipe_tile       mario_SmallPipe     1  1
Animation mario_SmallCloud_dec           mario_SmallCloud   1  1
Animation mario_SmallBush_dec            mario_SmallBush    1  1
Animation mario_BigBush_dec              mario_BigBush      1  1
Animation megaman_megaBuster_shot    megaman_megaBuster  1  1

# --- the gameplay tiles, and the coin a question block drops --------------------
#
# Four more one-frame animations, added by Phase 18 for the tile behaviour: a brick, the two
# states of a question block, and the coin.
#
# ### mario_Brick_tile is the ground tile's artwork, and that is the course's own mapping
#
# There is no brick artwork in this library. That is not an oversight in the import - it is
# a property of the course's asset library, and the course's reference resolves it by
# pointing its brick texture at the ground image:
#
#     Texture TexBrick ../bin/images/mario/ground.png
#
# So this is the course's mapping transcribed into this file's naming convention, not an
# invention. A brick is drawn with the ground block's 64x64 image, is therefore exactly one
# grid cell, and collides as exactly one cell - which is what makes it placeable in a level
# at all. Phase 13 declined to declare this because nothing had established the mapping; the
# course's `TexBrick` line is that establishment.
#
# ### The question block's artwork is real and cannot be a grid cell
#
#   mario_question_block   360 x 360
#   mario_question2_block  160 x 160
#
# Both are declared honestly, at the size they actually are. Neither is placed in
# levels/level1.txt, and the reason is arithmetic rather than taste: the course sizes a
# tile's bounding box from its animation, so a 360-pixel box in a 64-pixel cell would be a
# block five and a half cells wide that a player could not walk past, and no integer frame
# count expresses the image at cell size - frames are one row of equal columns filling the
# full height, so the height is always the texture's height. The behaviour is implemented,
# tested and reachable; the shipped level simply does not contain a tile whose artwork
# cannot honestly occupy a cell.
#
# The honest fixes are the same two this file already names for megaman_megaRun:
# re-author the strips at a width that divides evenly into cells, or add a per-frame offset
# or fit field to the animation format. Both are changes to the animation core rather than to
# the tile behaviour, so neither is made here.
#
# ### The coin is one frame because the coin spin strip cannot be sliced
#
#   mario_coin_pickup      500 x 299    library/images/mario/coin.png, a single coin
#   animations_coinspin    500 x 280    six coins, gutters 11, 31, 52, 56 and 35 px wide
#
# coinspin is genuinely multi-frame and genuinely unusable by this format: its transparent
# gutters are not equal, so no frame count that divides 500 lines the coins up with their own
# frames. Slicing it at 500/4, or 500/5, or 500/6 would put four, five or six *different*
# coins' worth of artwork into one frame - a misregistration, which is exactly what the
# divisibility rule exists to prevent. mario/coin.png is one coin, so a one-frame animation
# is a true statement rather than a placeholder. Phase 18 draws it through
# Transform::scale, which costs no geometry because a coin has no collider.
Animation mario_Brick_tile           mario_ground        1  1
Animation mario_question_block       mario_question      1  1
Animation mario_question2_block      mario_question2     1  1
Animation mario_coin_pickup          mario_coin          1  1

# --- the player's own animations -----------------------------------------------
#
# The course names three player states and three pictures: "The player Entity in the
# game is represented by Megaman, which has several different Animations: Stand, Run,
# and Air."
#
# Two of the three are declarable, and both are single frame:
#
#   megaman_megaStand   190 x 208   1 frame   -> Stand, and Run as well (see below)
#   megaman_megaJump    279 x 266   1 frame   -> Air
#
# ### Why there is no run animation, again
#
# megaman_megaRun is 733 pixels wide and the course declares it as 3 frames, so
# 733 / 3 is 244.33. 733 is prime: the only frame counts that divide it exactly are 1
# and 733. The divisibility rule above refuses anything else, and the block comment
# on megaman_megaRun in the animations section says what it would cost to round: each
# of the three run sprites would be misregistered by 2 to 6 pixels and the strip's last
# column would be silently discarded.
#
# Declaring the strip as a *single* frame was considered and rejected. It satisfies
# "three distinct player animations" on paper, and draws three run sprites side by
# side, 733 pixels wide, centred on a 40-pixel-wide player. A visibly broken picture
# introduced to satisfy a naming requirement is worse than a stated limitation.
#
# So the run **state** is implemented and observable and the run **picture** is the
# standing sprite. The honest fixes are the two this file already names for
# megaman_megaRun: re-author the strip to a width that divides evenly, or add a
# per-frame offset field to the animation format. Both are changes to the animation
# core rather than to the player, which is why neither is made here.
Animation megaman_megaStand_stand  megaman_megaStand  1  1
Animation megaman_megaJump_air     megaman_megaJump    1  1
